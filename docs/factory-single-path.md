## The design in ten lines

1. One interface: launch a batch job from a checkpoint; fresh means an empty checkpoint.
2. Build one immutable batch release from a clean git commit, including launcher, worker code, prompts and drivers.
3. Approve its manifest/fingerprint once; every case, retry and replacement uses those exact bytes.
4. Run bounded batch lifecycle ownership on the always-on control VM, independent of the Mac. Keep restore-key authorization behind the launch interface; implementation of the approved scoped VM key follows separately.
5. Store case progress, cumulative usage and completed evidence in checkpoints, never copied factory trees.
6. A single coordinator queues work and leases account capacity; a single launcher owns worker creation through deletion.
7. Provider limits checkpoint and wait for reset; the coordinator resumes automatically within batch bounds.
8. Completed unresolved G2 review gets one independent model-family review; conflicting judgments alone need founder judgment.
9. Exhausted rounds/budget queue a replacement immediately and diagnose the original; stream D defines code-checked extensions, factory-bug resumes and retirement within cumulative batch bounds. Infrastructure waiting/retry uses those bounds.
10. Keep sealed content, Mac-only founder identity, approved executable fingerprints, evidence checks and durable ownership; drop per-case launch ceremonies.

### Checkpoint and release contract

Interface: `launch(batch_id, job_id, checkpoint_generation_or_empty)`. One launcher implementation handles both inputs. Callers do not choose restore, salvage, gate-only, parked-worker, or rehearsal algorithms.

Batch record: git commit, one complete release manifest digest, pinned runtime/image and driver versions, role/model/effort assignments, authorized account labels, holder deadline, concurrency ceilings, ordinary case thresholds, no replacement count cap, and cumulative batch money/deadline bounds. Replacement chains share those bounds. Per-file hashes are bound by that digest; there is no second unused launcher fingerprint in the record. Build once; workers verify the same release before import or model execution. A fix creates a **new batch release**. Drain the old batch or explicitly migrate its checkpoints into the new batch, retaining lineage and invalidating affected evidence; never patch one case's code copy.

Checkpoint: case ID, parent generation, schema version, release digest, seed/admission reservation, current phase and pending operation, retained model handoff/findings, committed gate/calibrator receipts and their dependency hashes, rounds/calls/costs, account/reset metadata and retry counts. Private material stays encrypted. Public metadata contains only operational fields and hashes. Restore verifies the ciphertext/card pair, then verifies embedded accounting and evidence **inside the worker** before continuing. Incomplete operations rerun within original limits; completed receipts are reusable only when dependencies still match. A saved PASS label alone grants nothing. Usage and retry counts never reset with a worker or controller restart.

Use existing durable checkpoints, ledger import, gate bindings and calibrator receipts. Do not first invent a second event engine. Legacy checkpoints lacking trustworthy accounting/phase evidence are reconciled inside a worker or retired; a public-card edit cannot repair missing proof.

### Holder and control VM

`key_holder.py:serve` retains the identity until a monotonic deadline, accepts multiple `policy['jobs']`, starts separate launcher processes and prevents concurrent recovery of the same case. It locks/wipes identity memory and reserves launches before uncertain process starts. **No new holder is needed.** The batch mode adds a release binding, bounded jobs and concurrency, and durable generation reservations to this existing service.

The always-on **control VM** owns the coordinator, launch controllers, canonical public-card/ciphertext store and status queue. Reuse `control/` service/timer supervision, `control_resume.py` durable controller locks and R2 ciphertext storage. The Mac may sleep, lose power or lose its network without stopping lifecycle monitoring, collection or retirement. No new Mac unlock ceremony or Mac availability dependency is part of the batch interface.

The founder has approved a scoped VM restore key receiving an additional wrapping of eligible per-case keys. Its implementation is explicitly deferred: do **not** create that key, add a wrapping recipient, rewrap historical material or install VM restore authority in this slice. `launch(batch, job, checkpoint_or_empty)` accepts operational IDs and digests, never a private key, so the approved key service can replace the current authorization boundary without changing callers. The existing credentials-only control identity can launch fresh jobs and reclaim controllers; it still cannot restore a checkpoint. Consequently unattended checkpoint relaunch is not operational until the separate key implementation is complete.

**Batch jobs require `.casekey.age`.** The worker downloads ciphertext from R2 when a signed object is available; otherwise the controller uploads the frozen ciphertext. Both transfers use a timeout scaled from the actual ciphertext size: at least 1,200 seconds by default, or two seconds plus one second per 256 KiB, whichever is larger. The authorized host opens only the small wrapped case key and sends it through the protected channel to worker RAM. Never send the founder identity to the worker/control VM. Archive plaintext stays on workers for batch jobs.

**Legacy non-batch checkpoints remain restorable without a casekey.** They retain the existing host-decrypted streaming path until stream B migrates their keys on the control VM using the approved scoped restore key. Salvage finished work rather than strand it: the read-only local inventory contains 43 checkpoints, including 30 without casekeys. The batch-only rule is not retroactively imposed on that inventory. Historical rehearsal salvage and the legacy stream must retire after migration before a universal worker-only plaintext claim is justified.

Maintainers handle broken infrastructure; founder approves batch authority and resolves substantive reviewer disagreement.

## First-slice implementation and remaining retirement prerequisites

`factory/batch.py` builds a reproducible release from git objects using the shared launch manifest and the existing source installer/deployment adapter. Its single public `launch(batch, job, checkpoint_or_empty)` submits IDs/digests to the local control service. The same `launch.sh` installs the release for fresh and checkpoint jobs. Both public and archived cards bind its complete digest; worker accounting import verifies that binding and preserves the saved ledger. Exact checkpoint digests cross the durable reservation and frozen-input boundary. Live or uncertain durable reservations count against batch capacity after service restart.

Release building requires the selected commit to equal HEAD and the source tree to be clean, then runs `tests/factory/test_restore_inventory.py --require-inventory` from the executing factory checkout. Inventory discovery uses `git rev-parse --git-common-dir` to find the main checkout's canonical ciphertext, with the current checkout as a fallback even outside Git or when Git is unavailable. A developer/CI suite with no ciphertext skips loudly; that skip cannot authorize a batch build. The required build qualification fails before creating a release when inventory is absent or any applicable inventory check fails. It checks available checkpoints without requiring an unwrapped legacy archive or a 500 MB sample. Stream B must re-qualify its migrated store under Murphy row `new-single-path-1`. Wrapped legacy archives are checked for two public age-header recipient stanzas and a nonempty R2 object. Transfer logs name R2, local ciphertext upload or the legacy stream, including a static fallback reason without signed URLs. Job caps preserve the lower of explicit job arguments and batch bounds for both admission and runner execution.

Murphy register scope: this slice covers the complete-source/hydration path in **row 32 for new batch jobs** and parts of **rows 5, 19, 29 and 51** (stable job identity, location-independent interface, durable exact-generation ownership and restart completion reconciliation). No entire register row is claimed closed: VM restore-key implementation, automatic continuation/publication, rollout and fault qualification remain separate work. In particular it does not resolve row 37's mutable runtime image identities.
