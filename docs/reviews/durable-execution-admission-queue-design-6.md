**FAIL — revision 6 is not ready for its specified two-backend first checkpoint.** Two restart rules can accept a damaged database or reject a legitimate interrupted initialization.

1. **Blocker — missing durable tables are accepted after the database has been used.** The [queue design](/private/tmp/unbug-durable-execution-review-20261105/docs/designs/durable-execution-admission-queue.md:315) permits any durable table to be absent after a valid marker. On a used database, a lost `durable_scope_key` would be recreated by WP7’s eager constructor; a subsequent lookup could generate a replacement key, leaving existing encrypted artifacts unreadable. Missing ledger tables similarly lose accounting.

   **Minimal fix:** Allow an incomplete durable-table set only before any DBOS objects exist and while every present durable table is empty. The specified construction order creates all durable tables before DBOS launches. Otherwise, refuse before constructing a mutating seam. Test marked, used SQLite and PostgreSQL databases with a missing key or ledger table and verify that schema and data remain unchanged.

2. **Blocker — PostgreSQL’s accepted migration states omit legitimate crash boundaries.** The [fixture rule](/private/tmp/unbug-durable-execution-review-20261105/docs/designs/durable-execution-admission-queue.md:328) allows an optional index left by the next online migration, but requires the recorded version’s objects otherwise. In DBOS 3.4.0, migration 22 executes `DROP INDEX CONCURRENTLY` in autocommit and records version 22 in a separate transaction. A crash between those operations leaves version 21 recorded with its previously required index absent. DBOS also commits the `dbos` schema and an empty `dbos_migrations` table before migration 1; that state has no recorded nonempty migration version.

   **Minimal fix:** Enumerate marker-only and empty-migration-table states, plus the precise pre-DDL and post-DDL/pre-version states for each pending online **CREATE and DROP**, including invalid remnants where applicable. Test these with a disposable PostgreSQL database. Pin the fixture and runtime to DBOS’s current `use_listen_notify=True`, since that setting changes migration-created functions and triggers.
