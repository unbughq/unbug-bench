## Claims checked against the code

These claims in the draft are correct:
- **The gap is real.** `resolve_job` copies the root template's `requested_total_usd` to `-rN` jobs (`batch_service.py:36-39`). `authorize_locked` then grants it unchanged (`batch_money.py:307`).
- **Replay skips the money check.** In `_admit`, the replay `return` (`batch_holder.py:217-221`) comes before both the incidents check and `authorize_locked`'s aggregate check.
- **The aggregate already counts carried debit and unknown holds.** `aggregate()` adds `carried_debit_usd` to each job's larger of held and known floor (`batch_money.py:291`). `read_import` recomputes the carried debit.
- **Capping in `channel` covers dispatch and config use.** `load_locked` runs `channel` on every row and every ACK authority. `_post` and `_config` compare against those rows.
- **The qualifier really shares the path.** `tools/qualify-batch-inputs.py:35` calls `holder._admit` read-only.
- **The worker treats `committed_total_usd` as a lifetime ceiling** (`budget.py:716`, `:928`). So per-job authority of S+E really does limit new spend to E.
- **No schema means no behaviour change.** Production chains are untouched.

## Majors

**1. The design never says that a successor must keep every root template for the whole chain. (Manifest contract, lines 20-25 and 41-44.)**
- Three rules combine here:
  - every root template has an entry;
  - keys must be existing roots or their `-r1` child;
  - the whole `practice_admission` object must equal the predecessor's.
- Together they mean `record['jobs']` must hold the same roots across every carry. Stream D's beta-plumbing and beta-science releases carry only scenario 6, yet they must still keep templates for scenarios 5 and 7. The history rule is then what stops those two being admitted fresh.
- The existing helper `TransferTests.target()` (`test_batch_transfer.py:69-74`) drops unselected roots. A successor built with it will be refused once the schema is present.
- **Fix:** say this outright, and say how D's sequence maps onto it. Beta-fault is either a fresh chain root that lists scenarios 5-7 from the start (beta's E sums to $50 plus each S), or alpha carries into beta, in which case alpha must pre-declare beta's entries and cap, because the cap cannot rise. Either reading works, but the implementer should not have to discover which one applies.

**2. Carrying a queued, never-launched child has no production path, so the exam would rest on fabricated state. (Lines 39, 87-98; carry continuity.)**
- `prepare` needs `snap['money']['jobs'][child]` to exist and needs no operation for that child (`batch_transfer.py:205, 215`).
- In production, a money row is only created through `_admit` → `reserve`, and that always creates an operation. `test_queued_child_with_any_operation_refuses` confirms that such an operation blocks the carry.
- The only way a queued child gets a money row today is the test helper `derive()`, which calls `money.authorize_locked` directly (`test_batch_transfer.py:263`). The final exam, "transfer a root plus queued replacement with real saved ledger history", would rest on that state. `ENGINEERING.md` §4 says a fixture generated by the code under test proves nothing.
- This is also D's scenario 5 (beta-fault → beta-fixed with the queued child).
- **Fix:** record it as an open carry-over gap owned by `t3/batch-carry-over`, mark that exam as authored state that proves only the clamp arithmetic, or define the production path that creates the row. Don't present it as carry-continuity evidence.

**3. The draft doesn't spell out that its baseline rule refuses most historical $20 checkpoints. (Lines 30-38; cap authentication.)**
- At the boundary where the schema is first introduced, the rules are S = `previous.total_usd`, the carried commitment must be ≤ S+E, and old grants are neither raised nor reset.
- So a root carried from a batch with a $20 hold is admitted only if S ≥ 20 − E. With D's beta E of $7.50, that means S ≥ $12.50. Nearly all historical candidates will be refused.
- The preflight expects "old $20 case authority -> authenticated S + E". The draft delivers "S + E or refuse".
- Refusing is the safe choice, and lowering to S+E would hand back headroom that the objective forbids. Still, the consequence must be stated in the handback and the report, because it decides whether item (3) eligible inputs and D's candidate selection are feasible. If lowering is wanted later, it is a separately reviewed change to `prepare`/`read_import`/`imported_row`, which currently require committed == old held.

## Nits

- **Lines 67-68:** `MoneyWait('money_wait')` for permanent structural refusals (unlisted name, r2, nonzero S on a fresh child) matches the class's docstring. Note that nothing drains the queue (`batch_service.py:301` only lists it), so an r2 that can't be admitted stays queued for good, which is harmless. Say so.
- **Line 68:** the claim "No operation/config/money writes on refusal" is too broad. `reserve` calls `transfer.prepare` before `_admit`, so the first reserve in an unprepared successor writes `export.json`/`import.json` even when `_admit` then refuses. Limit the claim and the byte-unchanged test to an already-prepared batch.
- **Lines 76-78:** refusing practice manifests in legacy `authorize` adds a guard; it does not delete a path. `key_holder.py:720` still uses it. Reword the "deletes" claim honestly. The guard itself is needed: an alpha practice manifest with no carry and a root job would otherwise get the full requested amount.
- **Line 30:** "for a new empty job S must be zero" can be a static `check_manifest` rule when there is no `carry_from`. That catches bad manifests at load time, not at admission.
- **Line 18:** older code ignores unknown top-level keys, so a release built without the clamp would silently ignore `practice_admission`. The risk is low, since the manifest has to be in the release tree, but bumping the manifest schema when the field is present would fail closed for free.
- **Line 85:** "focussed manifest/cap tests" is vague. The midterm list mostly covers it; just name the test file, and note that it needs the same `del HolderTests` import trick as `test_batch_transfer.py:356`.
- **Heilmeier gaps:** the objective is jargon-heavy (S, E, carry-over boundary, ACK), and there is no explicit risks section, cost or timeline beyond "one offline cycle". The deletion list and Murphy rows (none closed) are covered.

## Zoom-out
- The scope is right and reuses existing pieces: the manifest, `aggregate`, `channel`, `_admit`, and the import snapshot chain. It adds no ledger or provenance store.
- The history rule is needed. A template-only root in a successor gets a new case ID, so `empty_input` would not catch it being re-admitted.
- The replay reordering is the smallest correct fix.
