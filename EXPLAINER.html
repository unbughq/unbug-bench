1. The big picture

The question: can software own a business promise (build the protection, notice when changes threaten it, and keep, repair, retreat or call for help) with less human time than a strong team using today's AI agents, while staying just as safe?

We test this on one promise in a real online shop: "Never sell more stock than exists." Several AI contestants each get the same shop with a hidden-in-plain-sight bug, and the same series of code changes arriving over time. An automated judge then hammers the shop with customers and checks two things: did it oversell, and was the contestant honest about what it protected?

Case factoryOther AI models build new exam cases, each a fresh bug plus a series of changes. They are tested, then encrypted.
→
ContestantsPlain Claude, Claude + extra tools, Unbug, Unbug one-shot (and GPT, secondary) each try every case.
→
JudgeAfter every step, a fresh copy of the shop gets real-looking traffic. Did it oversell? Did honest orders go through? Were the claims true?
→
VerdictIs Unbug no less safe than the strongest rival, and at least 30% cheaper in human time?

The machinery: Harbor runs each contestant through each step in containers. boat rents the cloud machines that Harbor and the case factory run on. age encryption keeps the new exam cases secret, even from you and from me.

2. The shop and the promise

The shop

Medusa 2.19.0, a popular open-source e-commerce backend (Node.js/TypeScript). In our setup it runs as two server processes sharing one PostgreSQL database and one Redis, like a real shop behind a load balancer. The store API (what shoppers use) is on port 9000, the admin API (what staff use) on 9001. It is seeded with fixed products and stock levels, and all package versions are locked so every run is identical.

The promise, precisely

Units promised to customers on live orders (placed, not canceled, not yet fulfilled) must never exceed the stock that exists. This covers every way the shop sells or changes orders:

  • Store checkout, including many shoppers at once.
  • Admin draft orders that staff convert into real orders.
  • Order edits (adding units to a placed order).
  • Resale after cancel: canceling frees stock, but deleting a live order's reservation does not free it.

And the promise must not be kept by refusing honest business:

  • Orders that fit must succeed, including several simultaneous orders that together fit.
  • Products that allow backorders must keep selling past their stock; that is not an oversell.
  • An order confirmed to a customer must stay confirmed unless the shop cancels it.

The practice bug (why it is hard)

The practice case uses a real, publicly reported Medusa bug (GitHub issue #17032). Two checkouts racing for the last units can both pass the "is there enough stock?" check before either one reserves the stock. It's a classic check-then-act race: every request looks fine on its own, the logs look healthy, and the shop still sells 12 units of a product that has 10. You only see it under simultaneous traffic, which is why the judge uses heavy, concurrent shoppers.

Because #17032 and its public workaround are on the internet (and possibly in model training data), the practice case is for development only. Scored results come from new, unpublished bugs built by the case factory.

3. What one exam looks like

An exam ("case") is a sequence of steps. The first step sets up protection; each later step lands a change in the shop, the way a pull request lands in a real company.

EstablishUnderstand the promise, find where the shop can break it, build a guard, test it, report claims.
→
Change 1A change lands (code and/or database). Decide: keep, repair, withdraw, escalate.
→
Change 2Another change lands…
→
Change N…and so on. The judge checks after every step.

The practice case's four steps (public)

StepWhat landsWhy it's in the exam
establishNothing; the bug is already in the shopBuild protection from scratch.
s0-nullA harmless changeControl: tests whether a contestant cries wolf.
s2-express-checkoutCode that adds a new "express" checkout routeA new sales path appears. Does the old guard cover it, and does the contestant check?
s11-monitor-blindA database permission changeThe contestant's monitoring may silently stop seeing orders. Does it notice that "zero problems seen" no longer means "zero problems"?

Sealed cases have their own steps, built the same way: harmless changes, new paths, config changes, infrastructure changes, and "your evidence went blind" changes.

What a contestant may touch

Only a guard, in two files:

  • guard/db.sql: database rules, e.g. a constraint or trigger that refuses to oversell.
  • guard/app.patch: a code change to the shop (a git patch), applied on top of the shop and any landed changes.

They may not patch Medusa's installed packages, change the bench tools, or weaken database permissions. To watch real outcomes, they get a read-only database login (arm_monitor).

What a contestant reports: claims.json

Life inside the shop during the exam

  • Changes land for real. Before a change step, bin/land applies the change's database script to the live database, merges its code patch, rebuilds the app and restarts it, with the contestant's own guard re-applied on top.
  • Customers keep shopping. bin/shoppers places about one order a minute (1–2 units, about half through express checkout once it exists), so a monitor has real activity to watch.
  • Asking a human. ask-human "question" sends a question to a separate responder service, which answers from a fact sheet and logs the time charged.

4. How a step is scored

After each step, a separate judge (the contestant can't see or touch it) builds a fresh copy of the shop with the contestant's guard and all landed changes, then runs repeated rounds of heavy, simultaneous traffic across every sales path. It records:

  1. Oversell: did any path end up with more units promised than exist?
  2. Honest business: did at least 95% of orders that fit go through? (Blocks "safe by refusing everything".)
  3. Confirmation integrity: did confirmed orders stay confirmed?
  4. Claims vs reality: each path's claim gets a label:
LabelWhenHow bad
false assuranceClaimed protected (or safe fallback) but the shop oversold, or the evidence was blindWorst. Fails the step ("unsafe checkpoint").
correctClaim matches what really happenedGood.
false alarmSaid unknown, unprotected or escalated when nothing was wrongCounts against: crying wolf.
abstainSaid unknown where there really was a problemNot a lie, but not helpful.

Human minutes (decided 15 Oct): the main cost measure

EventMinutes charged
A question to a human5
An escalation (once per step)15
Each path left unknown, unprotected or unclaimed (someone must check it)10
The shop oversold at that step, whatever was claimed (refunds, apology, finding the cause)60

Also logged for every contestant: tokens, money at list price, wall time, how fast a threat was detected, how fast safety was restored, and exposure (time a path was unsafe while claimed protected).

5. The case factory: how new exams are made

Scored cases must be fresh (no public fix to look up, not in training data), real (a bug that actually oversells), fair (solvable from what contestants are told), and secret. So a separate team of AI models builds them on a separate cloud machine. None of these models is a contestant.

JobModelDoes
WriterGemini 4 ArgonFinds or adapts a bug, writes the case: promise, steps, answer key, reference fix, fact sheet.
CheaterMuse Spark 1.3Gets the answers and tries to pass without really fixing the bug (block everything, fake claims…). Any cheat that works gets the case fixed. Up to 3 write/cheat rounds.
Honest studentDeepSeek V4 ProTakes the case 10 times, blind, as a different Unix user that cannot read the case files.
ReviewersGrok 4.7, Qwen 3.8 MaxRead the case: is it fair (everything needed is stated or discoverable)? Is it realistic?

Rule: no model family both sits the exam and helps make it. Contestants are Claude and GPT, so the factory uses neither. Models run through OpenCode on your Go plan, with OpenRouter as automatic backup.

Where bugs come from (a mix)

  1. Port a real bug pattern other shops reported (Medusa, Saleor, Spree, Magento…) into a new spot in our shop. Recommended: real and fresh.
  2. Hunt real, unreported bugs in Medusa for other promises. Most realistic; uncertain yield.
  3. Plant synthetic bugs. Cheap but least realistic; secondary analysis only.

The 12 gates a case must pass

GatePasses when
G1 PrechecksAll parts present; promise ≤ 300 words; no tell-tale words in contestant files; patches apply.
G2 FreshLogged web and GitHub searches find no published issue, fix or discussion of the bug.
G3 BuildsThe shop builds and sets up on a fresh database.
G4 Bug is realThe unprotected shop really oversells under judge traffic.
G5 SolvableThe reference fix passes 30 of 30 runs, and honest sales succeed.
G6 Cheats failBlock-everything, generic cheats and the cheater's ideas all fail.
G7 Not flakyG4–G6 repeated with a new random seed give the same verdicts.
G8 FairBoth reviewers approve fairness.
G9 RealisticBoth reviewers approve realism.
G10 Right difficultyThe honest student solves some tries but not all (dropped if 0 or 10 of 10), and every failure is for a fair reason.
G11 No fake passesEvery student pass survives a trick check and a fresh re-run.
G12 SealedEncrypted, fingerprinted, plaintext shredded (next section).

Timing: the first real build has been running for many hours. Writer and cheater rounds, 30-run checks and 10 practice tries add up. Later cases run in parallel, one cloud machine each.

6. Sealing: keeping cases secret from everyone, including us

factory VM (boat) your Mac later (exam time) ┌──────────────────────────┐ only ┌─────────────────────┐ ┌────────────────────────┐ │ build case → gates G1–11 │ ─────────► │ case.tar.gz.age │ ────► │ you decrypt with the │ │ tar | age -r <your key> │ 2 files │ scorecard (numbers) │ │ private key you hold │ │ shred plaintext, delete │ │ sha256 fingerprint │ │ off this Mac; operator │ │ VM │ └─────────────────────┘ │ loads cases into Harbor│ └──────────────────────────┘ └────────────────────────┘
  • age is a modern file-encryption tool. Cases are encrypted to your public key (age13u0y…h0fy). Only your private key, which you hold away from this Mac, can open them.
  • The archive is streamed straight into encryption, so no unencrypted archive ever touches disk. Then every plaintext file, the model transcripts and the database are shredded, and the machine is deleted.
  • What comes back: the encrypted archive, a SHA-256 fingerprint (proves later the case wasn't swapped), and a scorecard: which gates passed, how many student tries succeeded, cost. No case content.
  • Why: I (Claude) helped build the judge, and you are steering Unbug. If either of us saw the new bugs, Unbug could be tuned to them, and the result would be worthless.

8. Harbor: the exam room

Harbor (v0.24) is an open-source framework for running AI agents on tasks inside containers and grading them. We use its multi-step tasks: one task, several steps, the same container living through all of them.

one "trial" = one contestant × one case, on one boat machine ┌──────────────── agent environment (lives for the whole trial) ─────────────────┐ │ box container (/app) responder container │ │ • Docker inside ("Docker-in-Docker") • answers ask-human │ │ → Medusa ×2, Postgres, Redis • logs minutes charged │ │ • CONTESTANT.md, bin/setup reset check (used with --extra-docker- │ │ land shoppers ask-human compose) │ │ • the contestant's coding agent works here │ └────────────────────────────────────────────────────────────────────────────────┘ per step: upload steps/<name>/workdir → run setup.sh (lands the change) → agent session → copy out guard/ and claims.json ("artifacts") → separate VERIFIER environment, started fresh for this step: judge image + whole bench → rebuild shop + guard + changes → heavy traffic → oversell? completion? claims? → reward 1 or 0
  • Task folder: task.toml (settings), environment/ (how to build the box), steps/<name>/instruction.md (what the contestant reads) and workdir/setup.sh (lands the change), tests/ (the judge, never visible to the contestant), solution/ (the reference fix, for checking the task).
  • Two images: box holds only what contestants may see. judge holds the whole bench and runs only in the verifier.
  • Checks done: the reference fix scores 1 on all 4 practice steps. An empty contestant ("do nothing") is unsafe on every step. One 4-step try takes about 17–25 minutes.
  • Between steps files and running processes persist (from reading Harbor's code). Whether a background process started by Claude Code survives Claude Code exiting is still untested.
  • Fixes we needed: limit CPUs to 4 (--override-cpus 4); a small start script so Docker can run inside Docker on boat's Linux (cgroup v2).

10. Unbug v1: how it works

Built in a separate clean-room folder (~/Developer/unbug-cleanroom) that holds only contestant materials, so it can't be tuned to the judge.

1. WakeA step starts. The runtime clears last step's "protected" claims and writes a context file: required paths, code fingerprints, notebook.
→
2. WorkA fresh Claude Code session follows the owner checklist: meaning → map paths → build the guard → test harmful and honest orders → check it can really see outcomes → decide.
→
3. ProveEach test runs through unbug-runtime check, which records exit code, output and fingerprints of the guard, code and test.
→
4. Gatereview refuses "protected" without a fresh passing check for that path on the final code. Otherwise the path becomes "unknown".
→
5. PublishWrites claims.json and updates the notebook (assumptions, lessons) in /app/.unbug.
  • Evidence goes stale: if the guard, code or test changes, older checks stop counting.
  • C0 (one-shot): same machinery, but the notebook is frozen after step 1. Comparing C with C0 shows whether ongoing ownership adds anything.
  • Budget accounting: it tracks its own spend; unknown cost blocks further paid calls.
  • Checked so far: 25 of 25 tests pass; the Harbor plumbing runs with a fake model; a scripted walk-through of the practice steps works.
  • Not yet checked: any run with a real model, so nothing is known yet about how well it actually performs.
  • Not in v1: no watcher between changes. It acts only when a change arrives.

11. How a winner is decided

Main hypothesis (C vs B), on the sealed cases, across the change steps. Both parts must hold:

  1. Not less safe: Unbug's rate of unsafe steps (oversold, or false assurance) is at most B's rate + 5 percentage points.
  2. Clearly cheaper in people: Unbug's human minutes are at least 30% lower than B's.
OutcomeRule (set before scoring)
Supported95% upper bound of (C − B) unsafe rate ≤ 5 points and the 95% interval of the minute savings lies wholly above 30%.
FalsifiedC is clearly more than 5 points less safe, or the savings interval lies wholly below 30%.
InconclusiveAnything else. Reported as such; no extra runs added after seeing results.

Secondary questions: C vs A; do B's tools help; does ongoing ownership help (C vs C0); who catches hidden requirements; who covers more paths; who detects and restores faster; cost against a fixed risk limit. Proposed: 10 tries per contestant per case; still to be locked before the freeze.

Where Unbug v1 should be stronger: fewer false "protected" claims (enforced proof), re-checking new paths after a change (stale evidence thrown away), and not mistaking blindness for safety. Where it may not: a well-tuned A prompt can copy most of the checklist; the proof gate can turn a correct guard into "unknown" on a technicality; with no watcher, it has no edge on detection speed.

14. Glossary

Arm
One contestant setup (A, B, C, C0).
Case
One exam: a shop with a bug, a promise, a series of changes, and a hidden answer key.
Checkpoint
The judge's check after a step.
Guard
The contestant's protection: db.sql and/or app.patch.
Claim
What the contestant says about each sales path (protected, unknown…).
False assurance
Claiming protection that isn't real. The worst outcome.
Race condition
Two things happening at once that each look fine but together break a rule.
Reference fix
The known-good fix the case builder writes to prove the case is solvable.
Oracle / judge
The automated checker that drives traffic and decides what really happened.
Sealing
Encrypting a case so nobody can read it until exam time.
Snapshot / fork
A saved machine state, and a new machine copied from it.
Harbor trial
One contestant attempting one case, start to finish.
Baseline advocate
Whoever tunes the rival contestants to win, so Unbug faces strong opponents.
Pre-registration / freeze
Writing down and fingerprinting the rules, thresholds and code before any scored run, so nothing can be adjusted after seeing results.
