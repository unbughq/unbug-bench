Does an AI owner need less human help?

A pilot of unbug-bench

Unbug, grader team. Two practice rounds, six contestant versions, one public practice case.

Status: pilot. The scored exam on sealed cases has not run.

Background
Unbug is an AI that owns one business promise end to end: here, a shop must never sell more stock than it has. It writes the protection, maps every way to break the promise, says honestly what is and is not protected, and responds when the code changes. Our hypothesis: Unbug is at most 5 points less safe than a strong AI baseline and needs at least 30% fewer human minutes.
Methods
One public practice case on a real open-source shop (Medusa 2.19.0), in four steps: build the protection, absorb a harmless change, cover a new checkout path, and survive a change that blinds monitoring. Contestants ran on Claude Opus 5.5 at high effort unless noted: plain Claude Code, Claude Code with property-based and mutation testing, Unbug, a one-shot Unbug, and GPT 6.1 Sol via Codex. A separate judge rebuilt the shop and replayed heavy concurrent shopping traffic 30 times per step in round 1 and 10 times in round 2.
Results
Once our own grading error was corrected, every contestant kept the shop safe at every step: no overselling, no false claims, no questions to a human. In round 2 every contestant found and repaired a protection switch-off hidden inside an innocent-looking change. Unbug v0.1 used the model usage of plain Claude Code1 and took longer.
Conclusions
The pilot cannot test the hypothesis. With every contestant at zero human minutes there is nothing to reduce, and the safety interval is 98 points wide against a 5-point margin. Announced changes do not separate today's agents. The decisive test is a failure nobody announces, which only a contestant that keeps watching between changes can catch.

Primary endpoint, fixed before any run

What we tested

Every contestant sat the same four-step practice case inside its own container, with the shop running, a pretend shop owner it could ask questions (each question is charged as human time), and every web visit logged. After each step a fresh judge, which the contestants never see, rebuilt the shop, applied every change so far, and replayed bursts of conflicting orders to count oversold units, refused legitimate sales, and claims that did not match what happened.

  3. 3. New checkout pathExpress checkout appears. Notice it and protect it.
  4. 4. Monitoring goes blindRound 2: a privacy change hides orders and quietly switches protection off.

Where the grader was wrong

A benchmark is only as trustworthy as its own error log. These are every deviation we found in this pilot, in the order we found them.

  1. Round 1, step 4 failed four contestants for true claims

    The answer key counted any "protected" claim as false while the monitoring login was blind. But each contestant's own checker could still see orders, the protection really held (30 of 30 runs), and Unbug v0.1 and one-shot Unbug had rebuilt and self-tested their checks. The key punished careful and careless answers alike.

    CorrectionRegraded as pass. Step 4 redesigned for round 2 and graded on outcomes: "protected" is false only where the judge sees overselling.

  2. The contestants' checker was never actually blinded

    The step blinded one database login, while the contestants' standard checking tool used another that ignored the privacy rule.

    CorrectionRound 2 blinds every login a contestant can use. The judge reads through its own separate role.

  3. Fewer judge runs in round 2

    Round 2 replayed 10 traffic runs per step instead of 30, to finish the round the same afternoon.

    Accepted for the pilotThe scored exam is fixed at 30 runs per step under heavy traffic.

  4. One-shot Unbug is not yet paired

    The protocol's one-shot Unbug should continue from Unbug's own first session. Here it ran its own first session.

    OpenPairing needs cloning a live environment mid-try, which is not built yet.

  5. A wrong model name on the first launch

    Plain Claude Code's first round-1 launch passed the model name in a format the relay rejected. It stopped before doing any work, so nothing it did was graded.

    CorrectionRelaunched with the corrected name; the failed launch spent no usage.

What the pilot tells us

  1. Announced changes do not separate today's agents. In round 2 every contestant read an innocent-looking change, worked out that it switched protection off, proved it, and repaired it. "A change landed, check it" is a solved task at this difficulty.
  2. Step 3 did not test noticing a new path. Plain Claude Code, Claude + testing tools and GPT answered "keep" at step 3 in round 2 (GPT also in round 1) and still passed, because the protection they built in step 1 already covered express checkout at the database. Only the Unbug versions, and plain Claude Code in round 1, answered "repair". Future cases need a new path that first-step protection cannot cover by accident.
  3. Unbug's care is real but unscored. In round 1 Unbug v0.1 and one-shot Unbug both noticed their monitor had gone blind and rebuilt their checks with a self-test before claiming anything. Plain Claude Code relied on a checker that happened to keep working. Outcomes were identical, so the score is identical.
  4. Unbug costs more for the same result.
  5. The hypothesis lives or dies on unannounced failures. A per-change agent is only called when a change lands. If protection fails with no change, only a contestant that keeps watching can respond. That is the step this pilot did not contain, and what Unbug v0.2's watcher is for. Its first run is encouraging but not decisive: 8 seconds into step 3 it marked the new checkout path as uncovered, and 3 seconds into step 4 it marked protection and visibility as degraded; each state returned to healthy once the repair landed. It writes these as internal escalation records in Unbug's notebook, which the judge does not see or charge, and it made no model calls. A per-change session was running at the same moment both times, so this round cannot show that the watcher adds anything a per-change agent does not.

Limitations

  • One try per contestant per round, so no result here is statistically meaningful.
  • The practice case is a public, well-known Medusa bug. Models may recognise it.
  • Round 2 used 10 judge runs per step, not 30.
  • Checkpoints within one try depend on each other; intervals treat them as independent.
  • Usage dollars are list-price accounting, not invoices. GPT's is an estimate.
  • The redesigned step 4's switch-off reaches the live shop only on new database connections. It rewards understanding the change, not just re-running tests.
  • No outside reviewer has audited the judge yet.
  • Unbug v0.2 was frozen mid-afternoon and joined round 2 about 40 minutes after the others, on the same task and settings.

What comes next

A step nobody announces. Protection breaks between sessions with no change record. Per-change contestants are not called; only a watcher can catch it. This is the decisive test of the hypothesis, and it needs new harness support.

The scored exam. Five sealed cases, written and attacked by other model families, are in the case factory. Once one is sealed, every contestant takes it 5 times at 30 judge runs per step.

A stop rule written down before scoring. Proposed, not yet adopted: if Unbug is not clearly safer or more honest than plain Claude Code on the sealed cases, Unbug as a layer over a coding agent is not the product.

Methods

The judge

After each step a separate verifier container rebuilds the shop from scratch, applies every change so far and the contestant's protection, and replays heavy traffic: seeded bursts of 2–4 conflicting carts within 5 ms, crowds that exactly exhaust stock, admin edits, draft conversions, cancel-and-resell, and deleted reservations. It counts oversold units on every path and checks that legitimate orders still succeed.

Calibration on boat, 4 vCPU / 8 GB: unprotected shop oversold 30/30, refuse-everything passed 0/30, reference protection passed 30/30, zero harness errors.
